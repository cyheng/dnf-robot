## 入口与关键流程

### Robot 主进程

`cmd/robot.runMain` 的启动链路：

1. 解析运行模式；`--bounded-log-sink` 和 `--web-admin` 是同一二进制的独立入口。
2. 定位并加载主配置，创建 `/config` 分类目录，初始化滚动日志。
3. 释放运行时默认文件，校验/导出 PVF 资源，加载机器人运行配置并检查文件描述符容量。
4. 启动 route 0 sink，加载密钥，连接数据库。
5. 创建 RobotService、RobotManager、缓存失效客户端、监控/邮件能力和 MarketApp。
6. 启动运行时文件监听、TCP API、Web 管理子进程、自动机器人和市场任务。
7. 等待 SIGINT/SIGTERM，随后按 defer 的逆序关闭 Web、TCP、运行时监听、Market、Manager、RobotService、数据库、密钥、route 0 sink 和日志。

资源所有权：主入口拥有上述长生命周期资源。运行时文件监听必须在其消费者退出前停止；统一日志 sink 必须在日志文件关闭前解除绑定。

### Web 管理子进程

父进程通过 stdin 传入已解析的配置快照，避免子进程再次读取到不同版本的主配置。子进程用 `signal.NotifyContext` 驱动 HTTP Server 优雅关闭；父进程 Supervisor 负责异常退出后的重启和超时强制终止。

### 部署启动器

`tools/deploy-launcher` 是独立 Go 模块和 GUI 入口。部署或 VM 验证必须遵守 `doc/vm.md`，本轮审计不把它与 Robot 进程生命周期合并。

## 日志规范基线

当前日志分为四个出口：Robot 滚动日志、stdout/stderr 的有界收集文件、Market 独立结构化日志、协议诊断文件。第一阶段保持出口和既有事件文本不变。

后续新增或迁移的运行事件采用以下约束：

- 一行一个事件，以稳定的 `UPPER_SNAKE_CASE` 事件名开头。
- 字段使用 `lower_snake_case=value`，顺序为关联字段、状态字段、业务字段、`err`。
- 机器人使用 `uid`，角色使用 `cid`，请求/任务使用其稳定标识；禁止把标识只写在人类消息中。
- 成功、失败、降级和不可用必须由事件名或 `status` 明确表达。
- CLI 启动失败写 stderr；守护进程运行事件进入统一 Robot sink；协议大包和诊断数据继续使用专用诊断文件。
- 不在业务包内增加新的日志后端；统一经现有 `foundation/log` 汇聚。

已发现三种历史事件风格：`[Module] message`、`UPPER_SNAKE_CASE fields` 和裸文本。迁移必须按模块分批并保留诊断消费者所依赖的事件名。

## 分批记录

### 第一批：日志汇聚点生命周期

- 证据：`foundation/log.Robotf` 被 Scheduler、Actor、协议运行时、Web Supervisor、邮件和 Market 等并发 goroutine 调用；生产环境只有主入口设置 sink。
- 修改：使用原子指针发布/读取 sink，消除运行期替换或清理时的数据竞争。
- 修改：主入口关闭日志前解除 sink，避免关闭后仍把消息投递到无效文件后端。
- 修改：先停止并排空运行时文件监听，再关闭 Market，防止 shutdown 后的配置 Apply。
- 测试：补充并发替换与写入测试，本机重复执行 100 次通过。当前 Windows Go 环境未启用 CGO 且无 C 编译器，`go test -race` 留待 Linux/CGO 环境验证。
- 外部行为：日志文本、目标文件和回退到 stdout 的行为不变。

### 第二批：机器人默认配置一致性

- 证据：`robotconfig.Default()` 的 `create.jobs` 为 `0..9`，而嵌入并首次释放的 `defaults/robot_config.ini` 为 `0..10`；两条启动路径因此产生不同职业池。
- 处置：以已发布默认资源和当前 PVF 职业范围为准，将代码默认值及 `Normalize` 空列表回退统一为 `0..10`。
- 测试：运行时默认资源测试现在要求完整解析结果与代码默认值一致，防止后续默认配置再次漂移。
- 删除内容：无；这是默认值纠偏，不改变显式用户配置。

### 第三批：主配置死实现与重启诊断

- 证据：`SysConfig.ThisIP` 只有解析函数内部的临时复制用途；`DNFServiceRoot` 在生产代码中零引用，仅有孤立测试。
- 处置：删除这两个无消费者实现，直接在 `RobotConnectIp=auto` 分支解析本地 IPv4；不改变解析结果。
- 证据：Web `restartConfigDiff` 只比较端口、主机和密码，遗漏 `DfGameR`、服务组、数据库连接参数、日志滚动和 API 响应上限等启动期字段。
- 处置：补齐差异字段和诊断视图，并增加回归测试，确保磁盘配置变化会明确要求重启。
- 删除内容：`ThisIP` 字段、`DNFServiceRoot` helper 及其孤立测试；均无生产消费者。

### 第四批：运行时初始化日志出口

- 证据：运行时初始化在主入口建立 Robot sink 之后执行，但 4 个诊断分支仍直接 `fmt.Printf` 到 stdout，导致文件日志缺失且格式不一致。
- 处置：迁移到 `foundation/log.Robotf`，事件名统一为 `RUNTIME_*`，并补充路径和 `err` 字段；不改变初始化成功/失败分支。
- 删除内容：无；仅替换日志出口和事件格式。

### 第五批：Web 管理端日志出口

- 证据：认证、请求诊断和 HTTP Server 生命周期仍直接 `fmt.Printf`；父进程与 Web 子进程因此出现不同格式和出口。
- 处置：统一经 `foundation/log.Robotf`，事件名使用 `WEB_*`，保留子进程无 sink 时回退 stdout 的行为。
- 覆盖事件：会话创建、认证拒绝、请求 panic、响应写失败、慢/失败请求、监听、安全警告和优雅/强制关闭失败。
- 删除内容：无；仅替换日志出口和事件格式，HTTP 状态码及控制流不变。

### 第六批：TCP 基础设施异常日志

- 证据：`foundation/network.TCPServer` 捕获消息处理器 panic 后直接输出 stdout，无法进入主进程 Robot 日志。
- 处置：改用 `foundation/log.Robotf`，事件名为 `TCP_MESSAGE_HANDLER_PANIC`；panic 仍被隔离，连接清理和响应行为不变。
- 删除内容：无；仅替换日志出口和事件格式。

### 第七批：MarketApp 异常日志

- 证据：自动任务 panic 及市场服务 ensure/refresh 的错误曾直接输出 stdout；MarketApp 已有独立 JSON 事件日志，形成重复出口。
- 处置：写入现有 `appendLog(LogEvent)`，分别归入 `auto` 和 `market_service` 的 `failed` 状态，保留市场名及错误上下文。
- 删除内容：无；仅移除直接 stdout 输出，任务和服务控制流不变。

### 第八批：登录预检与令牌日志

- 证据：登录数据库预检和令牌生成失败仍直接 stdout；同包已有 `foundation/log` 汇聚点。
- 处置：统一为 `LOGIN_REPAIR_*` 和 `LOGIN_TOKEN_*` 事件，补充 uid/step/reason/err 字段，保留 fallback 与失败语义。
- 删除内容：无；仅替换日志出口和事件格式，登录返回结果与重试行为不变。
